# Deployment

SecureWall is a Windows desktop/controller plus LocalSystem service packaged as a per-machine WiX MSI. Debug output is `TinyWall/bin/Debug/SecureWall.exe`; the source directory retains its upstream name to minimize fork churn.

The product version has one source: `<Version>` in `TinyWall/TinyWall.csproj`. The SDK derives `FileVersion` from it (no `<FileVersion>` or `<AssemblyVersion>` override), `MsiSetup/Product.wxs` binds `ProductVersion` to `!(bind.fileVersion.SecureWallEXE)`, `.github/workflows/release.yml` refuses a tag that does not equal `v<Version>`, and `tests/installer/Test-SecureWallInstaller.ps1` asserts both the csproj value and the four-part MSI value. Bump all of them together, plus the `workflow_dispatch` default tag in `release.yml`, and add `docs/releases/v<Version>.md`.

In-place upgrades start with v0.5.0 (`docs/SECURITY.md`, "In-place upgrade"). Windows Installer compares only the first three version fields, so every release changes one of them; an equal three-part version is refused. `OldestUpgradeableVersion` in `MsiSetup/Product.wxs` (0.5.0) is the oldest installed version a newer package removes during its upgrade; anything older gets the "cannot be automatically updated" error. While `<Version>` is at or below 0.5.0, `MsiSetup.wixproj` passes `PreUpgradeVersion`: the floor becomes the product version and the upgradeable row is left out (ICE61 rejects an empty range), so v0.5.0 and the development builds before it upgrade nothing. CI also builds every installer as 0.5.1 (`Build-SecureWallRelease.ps1 -ValidationVersion`, written to `artifacts\version-check` and never uploaded) and checks that the upgradeable row and `RemoveExistingProducts` are in the package, so ICE validates that row on every push, before a release needs it. Three rules hold for every release from v0.5.0 on, because a later package cannot repair an installed one: its `/msi-upgrade-stop` and `/msi-upgrade-restore` must keep working; its full WFP cleanup stays provider-wide (every layer, every sublayer SecureWall's provider owns), which is what lets an older binary remove a newer version's objects after a rolled-back upgrade, so a release may register filters and sublayers on any layer under SecureWall's provider but no other object type (callouts, provider contexts), which v0.5.0 cannot delete; and it may write only recovery journal records every upgradeable older version can read. A release that cannot keep the last rule raises `OldestUpgradeableVersion`. Before tagging, review the `profiles.json` diff for widened definitions: an upgrade applies a changed definition of a profile the user already enabled at its first policy commit.

The v0.5.0 release notes need an **Upgrading** paragraph with this content: v0.4.2 and older cannot be upgraded in place, so uninstall SecureWall in Settings > Apps once, then install v0.5.0; from v0.5.0 on, running a newer MSI for the same architecture upgrades in place, keeps rules, settings and the password, and blocks connections to other computers while the service restarts, usually for under a minute; run setup at the computer's own keyboard and screen. Later release notes keep the in-place sentence and drop the one-time step once v0.4.2 is no longer offered.

`tools\vm\Build-SecureWallUpgradeFaultTest.ps1` builds the in-place upgrade VM test packages (configuration `UpgradeFaultTest`) into `artifacts\upgrade-fault-test\<version>`. They carry fault points (`TinyWall/Installer/UpgradeFault.cs`) and four stamps: an `+upgrade-fault-test` informational version, the assembly metadata `SecureWallFaultTest`, the MSI property `SECUREWALL_FAULT_TEST` and the ProductName "SecureWall (fault test)". Never attach them to a release: `Build-SecureWallRelease.ps1` does not know the configuration and refuses an executable with either executable stamp, and the installer contract test fails on a staged payload with an executable stamp or a package with an MSI stamp. Building them leaves the fault-test payload staged; the release builder restages its own.

There is no SecureWall binary update feed. The inherited TinyWall updater and its feed URL were removed from the code; upstream TinyWall updates must never replace this fork. The MSI has a distinct product name, installation/data paths, service, named pipe, WFP provider GUID, scheduled task, UpgradeCode, and auto-generated component GUIDs.

User-facing text and links name SecureWall and point at `https://github.com/ryanportfolio/SecureWall`, never at the upstream TinyWall repository (a core test scans the product for `github.com/pylorak`). TinyWall is named only where SecureWall detects or cleans up an installed TinyWall, in the GPL attribution and copyright notices, and in internal code names such as the `TinyWall/` source directory, namespaces and resource keys.

No signing, publishing, deployment, or real firewall activation is authorized by ordinary build work. Local unsigned test MSIs may be built without installing them. An explicitly requested public prerelease may carry unsigned test MSIs only when the release and README label them as unsigned and alpha. Release notes describe what changed for users; they carry no internal testing status (owner decision, 2026-11-01). Publishing one: after the version bump merges, create the GitHub release as a prerelease on the merge commit (`gh release create v<Version> --prerelease --target <sha> --notes-file docs/releases/v<Version>.md`; the notes file starts with the `# SecureWall v<Version>` heading followed by a `Website: https://secwall.org/` line); `release.yml` runs on the published release, builds the three MSIs, re-checks the tag and prerelease status, and attaches them with `SHA256SUMS.txt`. It refuses a non-prerelease, so a full release is a later manual flip of the prerelease flag on GitHub. Production shipping requires a successful release build, signed artifacts, GPL source availability, and the complete local-console matrix in `docs/TESTING.md`.

## secwall.org

https://secwall.org is a static site on the Vercel project `securewall` (team `sardonicasts-projects`). It is deployed from the CLI and not linked to Git. The live production deployment is the source of truth for its files; no repository holds them. Its JS bundle is prebuilt and its React source is not available, so version strings are the only edits it takes. The live site is the SEO version from ryanportfolio/SecureWall#15 (closed unmerged), deployed 2026-10-02 at v0.4.0: metadata, JSON-LD, a hidden crawler copy of the page text in `index.html`, `404.html`, `robots.txt`, `sitemap.xml` and a pruned stylesheet. That PR's branch keeps its preview server, SEO check and brand-image tools. The live `vercel.json` also redirects `/index.html` to `/` and caches `/build/*` immutable for a year, `/fonts/*` and `/webgl/*` for 7 days, and `/images/*`, `favicon.ico` and `apple-touch-icon.png` for 1 day. A changed file under `/build/*` needs a new name, including the LazareGrotesk, Magnetik and SpaceMono fonts that live there; a changed file under `/fonts/*` or `/webgl/*` reaches returning visitors within 7 days.

SEO work that needs the site owner: Google Search Console and Bing Webmaster Tools verification (a DNS TXT record at the registrar), extra indexable pages and copy changes. Work that needs the missing React source: the hero and section text start hidden for their reveal animations, and the single 1.29 MB bundle blocks first paint.

Every release updates the site. `release.yml` does this in its `site` job, after the MSIs are attached, by calling `.github/workflows/secwall-site.yml`. That workflow runs `tools/release/update-secwall-site.mjs`, which:

1. Downloads the deployment `secwall.org` points at, checking each file against the SHA-1 Vercel reports.
2. Reads the current release from the site's GitHub release links. It stops without deploying when the site already shows the tag, and refuses to move to an older version.
3. Replaces only `v<old>`, `Version <old>` and the JSON-LD `"softwareVersion":"<old>"` in `index.html` and `build/*.js`. The bundle also contains Theatre.js's own `"0.4.0"` state version, so a bare version number is never replaced.
4. Gives each edited bundle a new hashed name and updates every reference to it. `/build/*` may be served `immutable`, and an edit under the old name would stay cached in browsers.
5. Fails if any old version form remains, if `index.html` references a missing bundle, or if any new GitHub link or `SecureWall_<arch>.msi` asset does not return 200.

The workflow then deploys with `vercel deploy --prod` and checks that the live page links the new tag. It needs the `VERCEL_TOKEN` repository secret. After publishing a release, confirm the `site` job passed. To retry, or to update the site without rebuilding the MSIs, run `secwall-site` by hand with the tag (`gh workflow run secwall-site.yml -f tag=v<Version>`).

Flipping a prerelease to a full release is not automated. The site calls each release an unsigned alpha, so that change needs the user's copy decision and a hand edit following the same rules (version forms only, rename the bundle, deploy, check live).

To test locally, set `VERCEL_ORG_ID=team_kjAf51SrpxZhvAptYZizUMmB` and a `VERCEL_TOKEN`, then run `node tools/release/update-secwall-site.mjs --version <x.y.z> --out .tmp/site`. It writes the result to `.tmp/site` and deploys nothing. Outside CI a missing `VERCEL_TOKEN` falls back to the logged-in Vercel CLI (`vercel api`). Local-only flags: `--download <dir>` replaces `<dir>` with the live deployment and stops; `--from <dir>` updates a copy of a local site instead of downloading (the updater deletes `--out` first, so `--out` must not overlap `--from`); `--skip-link-check` skips the GitHub link checks for an unpublished version.

Headline redesign (`docs/plans/2026-10-31-secwall-headline-redesign.md`): `tools/site/patch-secwall-site.mjs --from <downloaded site> --out <dir>` applies two anchored bundle patches (one pushes each terrain instance onto `window.__swLayers`, the other exposes the post-processing composite pass as `window.__swComposite` for `SWText.lens`) and renames the changed bundle. It adds the library `tools/site/lib/swtext.js` and then every `tools/site/sections/*.js` in alphabetical order as `/build/sw-<name>-<hash>.js` script tags before the entry bundle, and joins `tools/site/sections/*.css` into one marked block in `securewall.css`. Re-running it on an already patched site replaces its own additions, including the older `sw-terrain-text-*` script. The library's header comment documents the `window.SWText` API the sections use; it attaches to both terrains (`Layers Hero` and the footer's `Layers Footer`). Each section names its meshes `sw-<section>` and marks its DOM elements `data-sw-section`. `prefers-reduced-motion` gets the same 3D version (owner decision); only a setup failure, such as no WebGL, leaves the DOM headings showing. `tools/site/serve-site.mjs <dir> [port]` serves a site for local review. Not yet on production.
