# Hardening release validation

This is the release gate for the pre-switch hardening change. Every live case below is **not yet run** unless an evidence record names the exact source revision, MSI hash, Windows build/architecture, VM snapshot, result, and supporting files. Source tests and packaging checks do not establish packet behavior.

Use a disposable Windows VM with working local/virtual console, a clean snapshot, and a second VM for inbound probes. Never exercise service termination, policy fault injection, audit changes, or installation on the development host. Build all Release MSIs, then prepare the bundle using `tools/vm/Prepare-SecureWallVmBundle.ps1`. Its guarded runner covers only the basic fresh-install path through the actual MSI.

## In-place upgrade (v0.5.0 and later)

These cases gate the v0.5.0 release. The sequence under test is in `docs/SECURITY.md`, "In-place upgrade"; the design is `docs/plans/2026-11-01-in-place-upgrade-and-updater.md`. Build the release packages under test (v0.5.0) and a later local test version (v0.5.1, never published, with `profiles.json` and `hosts.bck` changed) on a separate branch. Rollback cases need fault builds of either version: `tools\vm\Build-SecureWallUpgradeFaultTest.ps1` writes them to `artifacts\upgrade-fault-test\<version>`. A fault build shows "SecureWall (fault test)" in Settings > Apps and reads one fault point from the REG_SZ value `UpgradeFaultTest` under `HKLM\SOFTWARE\SecureWall` (64-bit view; set it from an elevated prompt, delete it to clear). The value is a point name, or `<version>:<point>` (for example `0.5.1:service-start-fail`) when both installed versions are fault builds. A point ending in `-pause` waits up to 10 minutes, until the value changes; every other point fails its step. Cancel in setup's progress dialog has no effect while a step runs, so a case rolls back from a pause by changing the value to the matching `-fail` point.

| Fault point | Version | Effect |
|---|---|---|
| `upgrade-stop-pause` | old | The stop step waits after its checks, before it writes the marker and turns off the restart actions (still on: a killed service restarts after 5 seconds) |
| `upgrade-snapshot-fail` | old | The stop step fails after copying the policy files, before the manifest (phase `stopped`) |
| `upgrade-stop-fail` | old | The stop step fails after finishing its snapshot (phase `snapshot-complete`) |
| `upgrade-restore-pause` | old | The restore step waits after restoring the snapshot (phase `restored`), before starting the service |
| `upgrade-restore-start-fail` | old | The restore step fails after restoring the snapshot, before starting the service |
| `upgrade-start-pause` | new | The start step waits before starting the service |
| `upgrade-start-fail` | new | The start step fails before starting the service |
| `upgrade-commit-pause` | new | The start step waits after the new service reports Running, before the transaction commits |
| `upgrade-commit-fail` | new | The start step fails after the new service reports Running; set it during `upgrade-commit-pause` to roll back from there |
| `service-start-fail` | either | The service fails during startup, before its first policy commit |

Each case captures the inventory listed below the main table plus, during the MSI run, WFP filter state polled as fast as the capture allows (target 250 ms; record the actual interval) and continuous external probes from a second VM. Record the MSI exit code, `installer.log`, the setup log, Application log entries, `sc qfailure SecureWall` and the `UpgradeInProgress` value before and after.
