# Hardening release validation

This is the release gate for the pre-switch hardening change. Every live case below is **not yet run** unless an evidence record names the exact source revision, MSI hash, Windows build/architecture, VM snapshot, result, and supporting files. Source tests and packaging checks do not establish packet behavior.

Use a disposable Windows VM with working local/virtual console, a clean snapshot, and a second VM for inbound probes. Never exercise service termination, policy fault injection, audit changes, or installation on the development host. Build all Release MSIs, then prepare the bundle using `tools/vm/Prepare-SecureWallVmBundle.ps1`. Its guarded runner covers only the basic fresh-install path through the actual MSI.

## In-place upgrade (v0.5.0 and later)

These cases gate the v0.5.0 release. The sequence under test is in `docs/SECURITY.md`, "In-place upgrade". Build the release packages under test (v0.5.0) and a later local test version (v0.5.1, never published) on a separate branch. Rollback cases need fault builds: `tools\release\Build-SecureWallRelease.ps1 -Configuration UpgradeFaultTest` writes them to `artifacts\upgrade-fault-test`. A fault build reads one fault point name from the REG_SZ value `UpgradeFaultTest` under `HKLM\SOFTWARE\SecureWall` (64-bit view; set it from an elevated prompt, delete it to clear). Both versions read the same value, and `service-start-fail` trips in every fault-build service start. So cases that fault the new version (`upgrade-start-pause`, `upgrade-start-fail`, `service-start-fail`) install the release v0.5.0 as the old version and upgrade to the v0.5.1 fault build; cases that fault the old version (`upgrade-stop-fail`, `upgrade-restore-start-fail`) install the v0.5.0 fault build and upgrade to the release v0.5.1.

| Fault point | Effect in a fault build |
|---|---|
| `upgrade-stop-fail` | The old version's stop step fails after it stopped the service and took its snapshot |
| `upgrade-start-pause` | The new version's start step waits before starting the service, until the value changes or 10 minutes pass |
| `upgrade-start-fail` | The new version's start step fails before starting the service |
| `service-start-fail` | The service fails during startup, before its first policy commit |
| `upgrade-restore-start-fail` | The old version's restore step restores the snapshot, then fails before starting the service |

Each case captures the inventory listed below the main table plus, during the MSI run, `netsh wfp show filters` polled every 250 ms and continuous external probes from a second VM. Record the MSI exit code and the `installer.log`, setup log and Application log entries.
