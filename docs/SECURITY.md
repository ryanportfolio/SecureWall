# SecureWall security model

SecureWall is default-deny host firewall software. A defect can either interrupt networking or permit traffic that should have been blocked. Treat install and real-network testing as privileged operations.

The Windows service remains start-pending until its first WFP default-deny transaction commits. If initialization fails, it stops instead of reporting a ready but unenforced state. A stop caused by failure reports `ERROR_SERVICE_SPECIFIC_ERROR` with service-specific exit code 1 (startup failed) or 2 (runtime recovery failed), never a clean exit. Service health configuration enables SCM failure actions for these non-crash failures: restarts after 5, 30 and 60 seconds, repeating the 60-second restart, with the failure count reset after one day without failure. A persistent cause therefore produces a restart attempt every minute rather than a permanent stop. Microsoft documents that the non-crash failure-actions flag takes effect the next time the system starts. Until the first reboot after installing, or upgrading from a build without the flag, a failure exit may not trigger a restart; the service then stays stopped behind the deny baseline until it is started manually, the controller starts it, or Windows restarts.

## Enforcement invariants

- Normal mode blocks inbound and outbound traffic unless a higher-priority explicit allow applies.
- The LocalSystem service owns WFP filters and stored policy. The tray controller cannot author a subject.
- A prompt is created only for outbound TCP/UDP drops whose runtime filter ID belongs to SecureWall's committed default-block ALE filters.
- Explicit user blocks and blocklists have higher weights and never become prompts.
- Allow uses an opaque, expiring, single-use service token. The resulting rule contains only outbound TCP/UDP connect wildcards; inbound listener fields remain unset. It merges into an existing permanent rule for the same subject only when the merged rule adds nothing but that outbound reach. A rule restricted to the local network stays a separate rule with its restriction and listener ports unchanged. Every exception merge follows the same limit: a merge never makes a LAN-only port or protocol reachable from other addresses. One local-network flag covers every port list in a rule, so when a single rule cannot express the union, both rules stay separate.
- Ignore, close, timeout, unknown token, expiry, ambiguity, lock, save failure, and reload failure all remain blocked.
- The popup stays open until the owner clicks Allow, Ignore or close, or the token expires. It never becomes the active window (`WS_EX_NOACTIVATE`), so keystrokes typed into other apps cannot answer or close it; only mouse clicks can.
- A prompt that leaves without an answer (token expired, or revoked by a policy change) is listed under "Blocked apps not answered" in the tray menu, and a balloon names it. The list lives in the controller and is display data: its tokens are dead and it grants nothing by itself. Allow from the list asks for confirmation and then uses the owner's normal exception path (`PUT_SETTINGS`, password lock, exception editor when enabled) to save the same outbound-only rule as the popup. Like the other tray whitelisting paths, it trusts the subject the controller shows, which came from the service's prompt. If that Allow asked for the password, SecureWall is locked again afterwards, including after a cancel or failed save, as Allow in the popup does.
- Always allow (popup button, or the tray list) saves the same exact-path allow plus a rule of file name and signer: the full subject of the certificate in the file's embedded Authenticode signature, accepted by `WinVerifyTrust` with whole-chain revocation checked against cached revocation data only. Windows can accept a chain whose revocation status is unknown (the development machine's LocalSystem trust settings allow offline revocation), so a revoked certificate is refused only when SYSTEM already holds a CRL or OCSP response for it. It is offered only for executable identities that Allow could grant, on a drive-letter path of a local fixed drive: the service never opens a UNC or WebDAV path for this check, because LocalSystem would authenticate to the host the path names. A path with a reparse point (symbolic link, junction, cloud placeholder) in any folder or in the file is refused too, since a link can point at a network host. That check reads attributes without following links, so a process that can create symbolic links (an administrator, or any user with Developer Mode on) and swaps a folder for a link between the check and the read can still make the service open a network path. From the popup the controller sends only the token (`ALLOW_PROMPT_ALWAYS`, password-gated like `ALLOW_PROMPT`) and the service reads and verifies the file itself before it takes the prompt-queue lock; from the tray list the controller reads the signer and saves through `PUT_SETTINGS`, as other tray whitelisting does. WFP cannot match a file name, so the rule is never a filter. When a later promptable drop comes from an executable whose name matches a rule, the service checks its signature outside the prompt-queue lock; only an exact signer match queues a service-only `AUTO_ALLOW_SIGNED` request, which adds an outbound-only exception for that exact path in Normal mode once it has checked that a rule still trusts that signer. A path that already has any exception (a block, an allow the owner limited to some ports, or a rule from an enabled special profile such as Windows Defender) is prompted instead of widened. Every other case (no embedded signature, catalog-only signing, another signer, a network path, a full request queue) prompts as before. A file that fails the check, or whose exception could not be added, is prompted without a new check for ten minutes while its size, its write time and the configuration stay the same. A name match with a bad signature is logged once per path, for the first 64 paths per service run. The first blocked connection from each new copy fails; its retry passes once the exception commits. Like any policy change, that commit revokes pending prompt tokens, so other prompts on screen move to "Blocked apps not answered". The rule trusts the publisher: any file with that name signed by the same certificate subject is allowed from any folder, including a user-writable one. The exception follows the path, not the file's contents, as every exact-path allow does: code running as the owner can copy a signed file into a folder it controls, run it so the service adds an exception for that path, then replace the file with its own program, which keeps outbound access with no prompt and no password. Replacing an already allowed executable in a user-writable folder works the same way without Always allow; Always allow adds that such code can pick new paths without the owner seeing a prompt (owner decision, 2026-11-01: documented, not closed). Removing a rule (Manage, Always allow) stops new automatic allows; exact-path rules already added stay until removed from the application list.
- Ignore in the popup sends `IGNORE_PROMPT`. Like closing the popup (`DISMISS_PROMPT`), it consumes the token and starts the five-minute cooldown. While the service is unlocked, it also saves the prompt's identity to the profile's Ignored list (`IgnoredApps`): an executable by exact path, a UWP app by package SID, or a service by name and path. The controller sends only the token, and the service takes the identity from its own queue entry. Shared or unattributed service hosts are never listed, because they have no exact identity. A later promptable drop whose identity matches an entry is not queued as a prompt. The drop stays blocked: the list adds no WFP filter and grants no traffic. Network Activity labels that drop "Blocked (ignored)", and it never reaches "Blocked apps not answered". Unlike Always allow, no entry matches by file name alone, so a copy of an ignored exe in another folder still prompts. While locked, Ignore keeps only the cooldown, because the list is a saved setting. The popup closes the same way whether or not the entry was saved; a failed save is logged to service.log. Saving it goes through the normal policy transaction; a change that touches only the Ignored list keeps pending prompt tokens. Removing an entry (Manage, Ignored) ends that identity's cooldown, so its next block prompts. Always allow is checked first: when the file also passes an Always allow rule's name and signer check, the service adds that rule's exception instead of ignoring the drop. The drop itself stays blocked, and the app's retry passes.
- Package identity accepts only an AppContainer package SID (`S-1-15-2-*`); null-SID sentinels are treated as no package authority. Service identity uses exact path plus service name. An ambiguous or unattributed registered service executable cannot be allowed from the popup. A service rule matches the per-service SID in the process token (`FWPM_CONDITION_ALE_USER_ID`), so a service whose SID type is NONE, or whose SID type SCM cannot report (shown as unverified, with read failures logged at most once a minute), is shown by name with Allow disabled rather than given a rule that never matches. SecureWall does not fall back to an executable-wide rule for it. An administrator who wants to allow such a service can run `sc.exe sidtype "<name>" unrestricted` (the popup shows this command with the name quoted), restart the service, and allow the next prompt; an update of that software may reset the SID type.
- Named-pipe clients must run from the exact installed SecureWall executable path in Debug and Release builds; Allow remains password-gated when the service is locked. This check is an image-path comparison, not a caller-identity boundary; see "Local IPC boundary" below.

The persistent and boot-time baseline denies all non-loopback traffic, including DNS and DHCP. It contains no recovery permits. All runtime policy, including saved allows, belongs to the service's dynamic WFP session. Service loss or startup failure withdraws runtime permissions and leaves strict external denial until the service successfully restores policy or explicit removal completes.

The baseline's WFP provider names no Windows service. BFE loads a service-owned provider's persistent objects only while that service is set to auto-start, so an earlier design lost the baseline at the next boot once the SecureWall service was Disabled or Manual. Now the baseline loads at every boot whatever the service start type. Disabling the service keeps external traffic blocked until an explicit removal deletes the objects under SecureWall's provider key, or until the service is set back to Automatic (`sc config SecureWall start= auto`) and started, which restores normal operation. Boot-time copies still end when BFE finishes initializing; the persistent copies take over. This rests on the `FwpmProviderAdd0` remarks, which state that BFE loads persistent objects whose provider specifies no service name. Other Microsoft pages describe it inconsistently: the `FWPM_PROVIDER0` and `FWPM_FILTER0` descriptions of the `DISABLED` flags read as if a provider without a service name were also disabled at BFE start. Only the "Service Disabled or Manual, then reboot" row in `docs/HARDENING-VALIDATION.md` settles it; until that row passes, treat start-type independence as unverified.

Withdrawal while running does not stop the service. It closes the dynamic session, then rebuilds a new one in-process: it re-reads adapter addresses and stored policy (including any pending recovery journal) and commits them, first immediately and then after 5, 15, 30 and 60 seconds. Nothing is granted before that commit. A rebuild restores the last runtime mode; like a restart, it expires until-reboot exceptions. Policy changes are refused until the rebuild commits. After five failed attempts the service exits with exit code 2 and SCM restarts it.

Address renewal and name resolution can fail during this interval. When the cause persists, such as a corrupt recovery journal or an unavailable Base Filtering Engine, every automatic attempt fails and recovery requires a local console.

The baseline deny uses `DefaultBlock - 2`, below the runtime default block so committed runtime filter IDs retain prompt authority. Disabled, LAN and WSL allowances do not survive independently of the dynamic session. BlockAll suppresses optional LAN and WSL permits. Until-reboot exceptions expire on service initialization or reinitialization; timed exceptions retain their absolute expiry.

WSL 2 filters are installed once per full policy reload, on each adapter whose alias is `vEthernet (WSL)` or `vEthernet (WSL (...))`, using the interface LUID from the same enumeration. A WSL permit that cannot be installed is logged and the reload continues; a WSL block that cannot be registered aborts the replacement like any other block filter. Mirrored networking has no such adapter, so the WSL_2 exception installs nothing there; other WSL-named adapters are logged, not filtered.

The Windows_Update database profile grants outbound TCP to the exact `wuauserv` service at its `svchost.exe` path. It supplies no executable-wide `svchost.exe` permission. Other Windows Update components need their own justified rules; update completion remains unverified.

Configuration changes journal the prior policy, then save and enforce the candidate before publishing success. Compensation starts whenever the candidate write is attempted, including a failure after the file was replaced. Failed compensation withdraws runtime grants. If journal completion fails after enforcement, runtime grants are withdrawn before further storage recovery is attempted.

An unresolved recovery journal must be restored before startup can load stored policy. Defaults are used only on confirmed configuration absence; corruption, decryption errors and access failures stop initialization rather than silently loading defaults.

Environmental reloads (address changes, display power changes, volume changes and the 30-minute housekeeping reload) replace runtime filters in one WFP transaction. If a reload fails before that transaction commits, the previously committed filters remain in force. The service keeps them only when the environment has not already superseded one of their grants: a successful adapter enumeration with no new addresses, no volume or mount change, and no pending display-off restriction. It retries after 5, 15 and 30 seconds. A fourth consecutive failure, a failure after commit, or a failure with a superseded grant withdraws runtime grants and starts the rebuild. An adapter enumeration failure leaves the address-scoped grants (local subnet, gateway, DNS) unverified, so it withdraws runtime grants at once. Only a later successful enumeration clears that state; a commit from a display, mount, settings or expiry change cannot. Timed exceptions expire through the minute maintenance pass, which never retains: any failure to apply an expiry withdraws runtime grants. A retained reload does not check expiry, so an exception that expires shortly before a failed reload can stay permitted until the next minute pass, up to about 60 seconds after its expiry time. A successful retry, 5 seconds after the failure, also omits it. Without a reload failure, expiry has the same one-minute granularity. Adapter address sets and the LocalSubnet, gateway and DNS filter conditions are published together only after every condition is built. A failed build clears the sets, so the next successful enumeration rebuilds every list and cannot reuse a partial one, which would silently narrow an address-scoped block. Default-block and block filter registration is strict, as is every other filter except the optional WSL 2 permit: a registration failure aborts replacement. A WSL 2 permit that cannot be registered is logged and skipped, and the replacement commits without it.

Background reads do not extend the ten-minute password unlock window. Only an accepted `UNLOCK`, `MODE_SWITCH`, `PUT_SETTINGS` or `SET_PASSPHRASE` (including a `PUT_SETTINGS` that the service answers with a stale-changeset retry warning and does not apply), an Allow that granted a valid pending prompt, or an explicit Ignore or close (`IGNORE_PROMPT`, `DISMISS_PROMPT`) that dismissed a valid pending prompt extends it. Popup timeouts use a separate `DISMISS_PROMPT_TIMEOUT` request that never counts, and prompt actions on unknown or expired tokens never count.

Encrypted output is finalized before the underlying file content is flushed with `Flush(true)`. Writers use a temporary file in the target directory, replace or move it into place, then flush the installed file. A post-swap flush failure can leave the candidate on disk even though the write throws.

The recovery journal supports process-failure recovery; ordinary file rename and journal deletion do not establish durable directory-entry ordering across power loss. A lost journal deletion could replay an older policy. Journal rename/delete power-loss ordering and physical-media persistence remain unverified. Content-flush calls and synthetic tests are not proof of either guarantee.

The journal is `config.recovery` beside the service configuration. An unreadable or corrupt journal deliberately prevents startup because the service cannot establish which policy was committed. Preserve it and the configuration for diagnosis. From the VM/local console, restore a known-good matching backup or use the installed MSI's full uninstall followed by a fresh install. If removal fails, restore the VM snapshot. Deleting only the journal could activate an uncommitted candidate policy; do not use that as recovery.

The controller authenticates the connected service before writing requests. The narrow Debug synthetic-pipe exception cannot select the production pipe. Prompt snapshots are reconciled against service authority, with at most 64 displayed/queued entries and an absolute token deadline independent of polling or AI reading time.

The service grants authenticated users only process-image query and lifetime-wait rights so the unelevated controller can retain a process handle and compare it with SCM's SYSTEM service configuration. It grants no process-write or token-query rights. Timed firewall exceptions are pruned on the minute maintenance pass and during rule reconstruction; they are not a second-precision cutoff.

Allow grants the identified executable, package or service permanent outbound TCP/UDP access to all destinations and ports. The displayed connection is an example of blocked traffic, not the scope of that grant. Executable rules follow a path, not a content hash. Publisher text is unverified metadata, not proof of a trusted signature.

## Learning mode (removed)

SecureWall has no Learning mode; blocked-connection prompts replace it. TinyWall's Learning permitted all traffic and turned whatever ran into permanent exceptions. The mode's enum value stays reserved so older messages and configurations parse. The service refuses a switch to it with an error and keeps the current mode. A stored or imported configuration (including a TinyWall `.tws` export) whose startup mode is Learning loads as Normal.

Exceptions learned by earlier builds stay in the profile. They are not detected or removed automatically, including an executable-wide `svchost.exe` rule with all TCP/UDP ports that TinyWall and SecureWall up to 0.3.0 could learn. Review the exception list after upgrading and delete such rules by hand. A service rule is never merged into an executable-wide rule for the same path; only subjects that are equal in both directions merge.

## Audit and attribution

WFP net events are authoritative for the drop and filter ID but do not contain a PID. Security event 5157 is parsed by field name and accepted only when filter ID, normalized path, direction, protocol, complete tuple, and timestamp match. SecureWall leases failure auditing by OR-ing it into the existing Filtering Platform Connection flags and restores the exact prior flags on disposal. The Security-event subscription reads only events 5157 and 5159 (a blocked bind, which includes raw sockets), and success auditing is never leased. Only 5157 feeds prompts. Both are also matched to blocked rows in the service's Network Activity log, by filter ID, normalized path, protocol, local port and a timestamp within five seconds, plus remote port, addresses and direction for 5157 (a 5159 is read only when SecureWall's own filter blocked the bind). Rows and audits that could pair up, in either arrival order, are grouped; a group's rows take the process ID only when all its audits name one process and it has no more rows than audits, The service decides each row once, after its five-second window has passed, when Network Activity reads the log; the event callbacks only record audits. It keeps the 256 newest audits, so a row read long after a burst of blocks can lose its audit and show no ID. Two processes with the same path and match key, or a lost audit, leave the rows without an ID. A lost row together with a lost audit from another process can still pair the wrong process. The tray app keeps the PID only while it belongs to a running process with that path that started before the block, and names its services from its current SCM view. The match feeds no prompt and adds no rule by itself, but Network Activity's actions use it: Unblock on a matched row adds one service rule per listed service (several rules save without the exception editor, as for any row with a live PID), and Close process ends the matched process.

The original flags are journaled to `HKLM\SOFTWARE\SecureWall\AuditRecovery` (64-bit registry view; value name is the subcategory GUID, DWORD value is the original flags) before the failure-auditing lease makes any `AuditSetSystemPolicy` change. An entry left by an earlier build's Learning success-audit lease holds the same original flags and restores the same way. The entry is written and flushed first; the live policy changes only after the write succeeded. Orderly service stop restores the flags and clears the entry. Service start, interactive `/uninstall`, and `/msi-cleanup` read the journal before any other audit work and restore whatever a crash, `FailFast`, `Process.Kill`, or interrupted MSI cleanup left behind, clearing each entry only after the backend accepted the restore. A malformed entry is skipped, kept in place, and reported by name so the healthy ones still restore; it never blocks uninstall because it holds no recoverable value. A healthy entry whose restore fails keeps its entry and aborts the uninstall (interactive `/uninstall` and `/msi-cleanup` return -1, so the MSI rolls back and the product stays installed), because the uninstaller removes the service that would otherwise retry, and it deletes `HKLM\SOFTWARE\SecureWall` once no journal holds a record; the log names the subcategory. A lease clears its own entry only after querying the live policy and finding it equal to the recorded original, so a nested lease whose restore failed cannot be masked by an outer lease that changed nothing. Whether a machine's audit policy was in fact returned to its original state after a crash remains a live-VM check, not a unit-test result.

If auditing or PID/service lookup fails, attribution degrades without weakening WFP policy. Subscription health, coalesced error/suppression counts and controller notifications are intended to make this visible without a per-drop log flood; restart recovery and UI delivery still require VM validation. A failed Security-event subscription stays unavailable until service restart after event access is repaired. There is no subscription retry; disposal detaches the watcher under its lifecycle lock, then waits for callbacks after releasing that lock. Late records and errors from an inactive watcher are rejected. SecureWall also inventories registered Win32 service image paths, following CreateProcess rules: a quoted first token is exact, and an unquoted command resolves only when its first whitespace-delimited token ends in `.exe` and no later `.exe` follows (or the whole command has no extension, which gains `.exe`). A `.exe` inside a directory or file name is not an executable boundary. An unquoted command with spaces before its executable stays unresolved because CreateProcess would probe shorter prefixes first. An unresolved registration keeps Allow disabled only for executables whose file name, or name without `.exe` at a token end, appears in that command; the service log names the registration once per change. Registrations without a text image path are skipped and logged, because SCM cannot start them. An unreadable inventory makes every executable without exact SCM attribution non-allowable. Both cases are shown as unconfirmed service registration, not as a shared service host. A registered service executable without exact attribution remains non-allowable. Executable warnings inspect file ownership and mutation rights as well as parent-directory replacement rights. These observations can change after display and do not pin executable content.

Exactly correlated drops enter a bounded queue of 64 entries. Each 250 ms timer pass drains one batch before acquiring a fresh bulk SCM process snapshot, shared only within that batch. Another batch always reads SCM again. Correlation callbacks do no SCM work and skip admission if a policy transition holds the queue lock. Capacity, contention, and a two-second publication deadline suppress work with coalesced diagnostics; suppressed connections remain blocked. Policy replacement, mode publication, and shutdown clear pending tokens and invalidate in-flight batches. Snapshot failures and shared service processes remain non-allowable. Call-count tests verify batching; they are not a performance benchmark.

## Local IPC boundary

The controller pipe is created with a DACL that grants Authenticated Users read and write access. On each connection the service resolves the client's PID with `GetNamedPipeClientProcessId`, reads that process's image path, and accepts the connection only when the path equals the service's own executable path (`PipeClientAuthorization.IsExpectedExecutable`). That is the whole server-side check: no token, session, or signature comparison, and no per-request re-authentication. The controller performs the mirror check on the server (image path plus SCM service identity) so a fake pipe cannot impersonate the service.

The consequence is that any process running as the same user can start the installed `SecureWall.exe` in controller mode, or drive an already running controller, and send every request the controller can send. That includes `PUT_SETTINGS`, which replaces the service's full configuration (every exception, mode-independent settings, blocklist and hosts options) in one message when the changeset matches, and `MODE_SWITCH`, `SET_PASSPHRASE`, `STOP_SERVICE`, `ALLOW_PROMPT` and `ALLOW_PROMPT_ALWAYS` (message types above 2047; types above 4095 are service-internal and rejected from the pipe). The application password is the only gate on those messages: while the service is locked they return `RESPONSE_LOCKED`; while it is unlocked (no password set, or within ten minutes of the last successful user action after `UNLOCK`) they are applied. This pipe design is inherited from TinyWall and is unchanged in SecureWall; an operating-system administrator can in any case stop the service through SCM. The prompt messages are SecureWall additions: a same-user process can still extend the unlock window by dismissing a real pending prompt with `DISMISS_PROMPT`, because the service cannot tell an owner's Ignore click from a forged one; each dismissal suppresses that identity's prompts for five minutes. While the service is unlocked, `IGNORE_PROMPT` on a pending prompt also adds that identity to the Ignored list. `READ_PENDING_PROMPTS` is unprivileged, so a same-user process can silence prompts for any pending app, its own or another's, until the owner removes the entry in Manage; that traffic stays blocked. Set a password and keep the service locked when unattended.

## Prompt popup input

The popup runs in the unelevated controller at the owner's integrity level, so any process running as the same user can find it and press Allow, or Always allow, which also saves a rule for any folder, on its own prompt (`BM_CLICK`, `SendInput`, UI Automation). Windows gives an `asInvoker` window no reliable way to tell synthesized input from the owner's, and the popup does not try. With no password set, nothing stops a same-user process from allowing itself; this is the same boundary as the pipe above. **Setting a password and keeping SecureWall locked is the control.** While locked, a synthesized Allow or Always allow reaches the service as `ALLOW_PROMPT` or `ALLOW_PROMPT_ALWAYS` and is refused until the password is entered.

The popup adds timing mitigations for accidental and click-timing grants:

- No key is bound to Allow, Ignore or close. The popup never becomes the active window (`WS_EX_NOACTIVATE`, and `MA_NOACTIVATE` on click), so keystrokes go to the window you are typing in. Other programs running as you can still press its buttons, as described above.
- Allow stays disabled until the popup has been visible, without repositioning itself, for about one second (checked on a 250 ms timer, so 1.0 to 1.25 s) and the executable risk probe (unsigned, user-writable location, recently changed) has finished and its warnings are on screen. Only the popup's own repositioning restarts the delay and disarms Allow again: when it is shown, grows to show risk warnings, or opens or closes the AI panel. The popup is borderless and cannot be dragged; a move or resize caused by a display change or another process does not restart the delay. The click handler rechecks the same condition, so a click on a disabled Allow does nothing.

These stop a keystroke or a click already in progress from landing on a freshly shown Allow. They do not stop a same-user process that waits out the delay.

When the service is locked, Allow opens the same password dialog as the tray. The popup stays open until the service token expires (two minutes after the service issued it), so it cannot close while the owner types the password. The token expiry does not move. After a successful unlock the popup retries Allow with the same token, then sends LOCK. The unlock is global, not scoped to the prompt: from UNLOCK until LOCK (one Allow round trip: two pipe requests, not measured here, and up to the pipe read timeouts if the service stalls) the service accepts every privileged request from any SecureWall.exe controller, as it does for the ten minutes after a tray unlock. Code that could use that window already runs as or inside a SecureWall.exe at the owner's level and could also read the password as it is typed; the popup unlock shortens the exposure of the previous tray-only path but does not remove it. Scoping the password to one Allow needs a service request that checks the password without unlocking; this build does not have one. The popup sends LOCK whenever it asked for the password, including after a cancel, a wrong password or a failed unlock request, because the service may have applied an UNLOCK whose response was lost; LOCK on a locked service changes nothing. If the owner cancels or the password is wrong, the connection stays blocked and the popup stays open for another try. A failed LOCK is not reported in the popup; the tray Lock item stays visible and the service's ten-minute inactivity lock still applies. Because a same-user process can press Allow and so make the password dialog appear, enter the password only for a prompt whose identity, path and warnings you recognize; the popup stays visible beside the dialog.

## Operational safety

Never install SecureWall over RDP, SSH, remote PowerShell, a cloud-only console, or any machine where losing networking prevents recovery. Use an expendable Windows VM with a snapshot and working local/virtual console. Do not install TinyWall and SecureWall together.

The MSI checks TinyWall's registry identity, and shared registration, controller recovery and service startup paths check the Service Control Manager. Activation refuses coexistence. Direct installation additionally requires a protected tree below Program Files, including every executable, DLL and ancestor; extracted bundles are not install locations. Keep TinyWall installed on the real machine until SecureWall completes the isolated VM matrix; then uninstall TinyWall and reboot before a SecureWall installation. To go back to TinyWall, uninstall SecureWall first.

The service runs the TinyWall and protected-tree checks before it loads policy and stops if either fails. After its first policy commit it runs them once more. A failure at that point (a TinyWall service registered meanwhile, an ACL change, or a transient read error during the tree walk) is logged and shown as a tray warning. The service keeps enforcing the committed policy, because stopping would withdraw it, and skips its service-restart and controller-task refresh. Install and repair paths still refuse on these checks.

SecureWall registers its persistent sublayers under its own GUIDs; builds up to v0.3.0 reused TinyWall's sublayer GUIDs. SYSTEM `/install` (before any service or WFP change; the protected data directory and its shipped defaults may already be written by then) and every baseline registration at service start (inside the baseline's WFP transaction) read the WFP state and refuse in four cases: TinyWall's provider `{66CA412C-4453-4F1E-A973-C16E433E34D0}` is registered; a sublayer with a TinyWall GUID belongs to any provider other than SecureWall's; a sublayer with a current SecureWall GUID belongs to another provider; or another provider's filter, or a filter with no provider, sits in a SecureWall or TinyWall-GUID sublayer. The error names each object found and the matching cleanup step; filters are inventoried on SecureWall's 14 layers only. For TinyWall objects: remove TinyWall with its own uninstaller (reinstall it first if it is already gone), reboot, and confirm `netsh wfp show state` no longer contains `66CA412C`. For objects of other software: uninstall the software that owns the named provider, reboot, and confirm with `netsh wfp show filters` that the named filters are gone. At service start the refusal leaves the previously committed persistent baseline in place, so enforcement stays at strict external deny.

Removal (baseline re-registration, `/uninstall` and MSI cleanup) deletes SecureWall's filters, then only the sublayers that SecureWall's provider owns under either the current or the TinyWall GUIDs, then the provider. A sublayer or provider deletion failure aborts the WFP transaction instead of being ignored. Another provider's filter in a SecureWall-owned sublayer makes removal fail before any WFP change, and the error names that filter when it sits on one of the 14 layers SecureWall uses, which the inventory reads. A filter on any other layer that references a SecureWall sublayer is not named: the sublayer deletion then fails with a generic `FWP_E_IN_USE` error and the transaction rolls back the same way. At service start this leaves the committed baseline unchanged. During `/uninstall` or MSI cleanup only the WFP state is unchanged: by then the service is stopped, controllers are closed, and hosts, Windows Firewall compatibility state and audit policy are already restored. The persistent baseline stays, so the machine stays at strict external deny with no prompts and no saved allows. MSI rollback runs `/install`, which fails the same check, and later service starts refuse too, so the service stays stopped. From the local console, remove the software that owns the named filter, reboot, and run the uninstall again.

Machine data is guarded separately from executable installation. The MSI places both defaults under protected `INSTALLDIR/data-defaults` and has no ProgramData file creation, write or deletion components.

Before timing, logging or policy access, the Release entry validates machine data; SYSTEM `/install` may create a missing directory with a protected ACL. After full-tree validation it brings the shipped data files `profiles.json` and `hosts.bck` to the content in `INSTALLDIR/data-defaults`: an absent file is created, a byte-identical file is left untouched, and a different file is replaced through a temporary file in the protected directory. A reinstall therefore delivers database fixes such as the Windows Update profile change. Configuration, password, `hosts.orig` and recovery journals are never written by this step, and the tree is validated again afterward. The shared production data-path accessor also enters the guard. Existing unsafe owners, writable descendants, untrusted mutation rights and reparse ancestors are rejected without blessing the tree.

A disappearing temporary child during atomic replacement is tolerated only after its parent is revalidated; missing or unsafe roots remain errors. Debug synthetic paths do not prove the installed Release guard.

Hosts enable/disable failures propagate into configuration or cleanup failure. Hosts file locking (`LockHostsFile`) is different: it is best-effort and never blocks WFP policy. A missing hosts file is neither created nor locked, and nothing is logged or shown for it; a hosts file that another program creates later stays unlocked until the service next applies its settings (service start or a settings or mode change). A hosts file another program holds open is logged in the service log and shown as a tray warning while the policy change proceeds. A lock lost after a hosts write is shown as the same tray warning but is recorded only in the optional diagnostics journal, not in the service log. The lock only denies other writers while the service runs; it is not an ACL. A missing original hosts backup is a valid never-enabled case; an unreadable backup is an error. A failed restoration retains its backup and must prevent successful teardown. Verify actual hosts bytes and failure ordering in the VM before accepting removal.

MSI repair and modification are rejected before changing the installation. From v0.5.0 on, a newer package upgrades the installation in place (see "In-place upgrade" below); v0.4.2 and older need explicit full removal followed by a fresh install. MSI maintenance uses a separate SYSTEM-only, noninteractive cleanup path; interactive removal retains confirmation and password handling. Cleanup must stop the service and restore owned Windows Firewall compatibility state before removing the persistent deny baseline. An administrator can stop the service through SCM; the application password is not an operating-system administrator security boundary.

The Windows Firewall service (`MpsSvc`) is a prerequisite for compatibility management. A disabled service must be restored to a supported configuration before installation. Recorded compatibility state must still be restored before the deny baseline can be removed. If Windows defers service deletion because another program holds a service handle, close service-management tools or reboot before reinstalling.

Compatibility rules use reserved exact identifiers and a reserved group. Original notification settings are journaled durably before mutation and retained until restoration completes. Old builds used random names and did not record original settings: their orphan rules and historical notification values require an explicit migration audit against a known baseline. This version does not guess ownership from a substring or reconstruct missing history.

Recovery order in a test VM:

1. Use the VM/local console, not the network.
2. Uninstall SecureWall from Windows Apps, or run the installed `SecureWall.exe /uninstall` elevated.
3. Reboot and verify the SecureWall service, scheduled task, provider filters, and compatibility rules are gone.
4. If ordinary uninstall fails, preserve logs and the VM snapshot for diagnosis; do not improvise broad WFP/registry deletion commands on a real machine.

### In-place upgrade

From v0.5.0 on, running a newer `SecureWall_<arch>.msi` over an installed SecureWall upgrades it in place, and the persistent deny baseline stays in force the whole time. v0.4.2 and older cannot be upgraded this way: their cached packages refuse to be removed by another package's upgrade, so setup stops with "An older version of SecureWall is installed that cannot be automatically updated" before changing anything. Moving from v0.4.2 to v0.5.0 is therefore the last explicit uninstall and fresh install. Setup also refuses, before any change, an equal version (a rebuild has a new ProductCode and would otherwise install beside the old one), a newer installed version, a package for a different processor architecture than the installed one, and an installation whose directory is not recorded. Windows Installer compares only the first three version fields, so every release changes one of them. Repair and modification stay unsupported.

`RemoveExistingProducts` runs immediately after `InstallInitialize`, so removing the old version and installing the new one share one transaction and one rollback script. Each version handles its own side of the swap with its own executable, which runs as SYSTEM from the protected Program Files directory. Every step receives the new package's ProductCode as its transaction ID. The upgrade installs into the directory recorded in `HKLM\SOFTWARE\SecureWall\InstallDir`, which is where the registered service's `ImagePath` points.

1. The old version runs `/msi-upgrade-stop` before its files and registry values are removed. It checks the LocalSystem token, the protected installation tree, the machine-data tree and the LocalSystem service registration as `/msi-cleanup` does. A snapshot an earlier attempt of the same package left behind is moved aside to `<transaction>.previous-<UTC time>` (never restored or deleted automatically; a warning names it), so this attempt's rollback can only restore a snapshot this attempt took. The service must be Running: one that stopped after a crash may have an SCM restart queued, which no later setting change cancels, so setup refuses that state; start the service, then run setup again. MpsSvc and BFE must be running too, so the new service can start. Only then does it change anything:
   1. It writes the upgrade-in-progress marker with phase `stopping`.
   2. It turns off SCM restart-on-failure and checks again that the service is Running. Failure actions apply when a failure happens, so a crash after this point queues nothing, and a crash just before it fails this check and aborts. The start type stays Automatic, so a reboot still starts whatever service is present.
   3. It stops the service with the normal bounded graceful stop, closes this installation's tray controllers in every session and fails if any is left, then sets the phase to `stopped`.
   4. It checks that the service is still Stopped (a controller that read the marker too early could have started it), copies `config`, `config.recovery`, `pwd` and `hosts.orig` into `%ProgramData%\SecureWall\upgrade\<transaction>\` with the password file's protected ACL (the tree's inherited ACL lets Users read), checks Stopped once more and writes a SHA-256 manifest of the copies as its last file. Then it sets the phase to `snapshot-complete`.

   Any failure here returns to the MSI, which rolls back before a file changes.
2. Windows Installer removes the old files and the old `InstallDir` and `Platform` values, installs the new files into the same directory and writes both values again.
3. The new version runs `/msi-upgrade-start`. It requires the service to be registered to this executable and stopped, a marker for this transaction with phase `snapshot-complete`, and a snapshot whose files match its manifest. It brings `profiles.json` and `hosts.bck` to the new package's content, deletes snapshots of other transactions, reapplies the start type and controller logon task, starts the service and waits up to 120 seconds for SCM Running, which the service reports only after its first policy commit. Restart-on-failure stays off: a service that exits during startup fails this step at once instead of being restarted.
4. After the transaction commits, `/msi-upgrade-commit` turns restart-on-failure back on, deletes the snapshot and the marker, and full-UI setup starts the tray for the installing user. The commit step's failure cannot undo a finished upgrade; it is logged (event 1001), and the next service start outside an installation restores the restart actions. The upgrade never runs `/autowhitelist`, so it cannot widen saved exceptions; new application profiles in the refreshed `profiles.json` reach users only through the Manage window. A changed definition of a profile the user already enabled takes effect at the first commit, so each release reviews the `profiles.json` diff.

While the marker is present and Windows Installer runs an installation, the upgrade alone owns the SCM restart actions: the service's own `EnsureHealth` at start, which normally turns them on, leaves them alone. Only the commit and restore steps turn them back on. So no restart can be queued for either binary from step 1 until the upgrade ends, and the start type never has to change.

A failure in step 2 or 3, or a cancel after step 1, rolls back in reverse order. Once the script has reached step 3, `/msi-upgrade-abort` (new executable) confirms restart-on-failure is off and stops the new service; a service that ignores the stop is terminated after its process is authenticated, as in failed first-install rollback, and its start type is set back to Automatic, which that termination path changes. It also closes controllers, and it leaves the registration, the start type, the marker, the snapshot and the baseline as they are. Windows Installer then puts back the old files and registry values, and `/msi-upgrade-restore` (old executable) runs last. It is idempotent: it can run after step 1 failed at any point, after a failed abort, or after a reboot mid-swap, and it decides from the marker phase, never from the service state alone, because a Running service at that point can be the new binary.

- No marker for this transaction, or phase `stopping` with the service still Running: the old service never stopped. The restore step refreshes the old shipped data, turns the restart actions back on and makes sure the service runs.
- Otherwise it first stops whichever binary runs, closes controllers and confirms Stopped. If the service cannot be stopped, it keeps the snapshot and the marker and fails, leaving recovery to the local console.
- A snapshot whose files match its manifest is restored as an exact set: each listed file is written back byte for byte, `pwd` with the secret-file ACL, and each covered file the snapshot does not list is deleted (a failed new service can leave a newer-format `config.recovery`).
- Phase `stopping` or `stopped` with no verified snapshot: step 1 never finished, so the live files are still the old version's own. The unfinished snapshot is discarded.
- Phase `snapshot-complete` with a missing, unreadable or non-matching snapshot: the new version may already have rewritten the live files, so the old service is not started on them. The marker and whatever is left of the snapshot stay, the step fails, and the deny baseline keeps blocking until local-console recovery; event 1001 names the snapshot path.
- In every case that continues, it brings `profiles.json` and `hosts.bck` back to the old package's content, turns the restart actions back on, starts the old service, then deletes the snapshot and the marker.

The old version also has to clean up after the new one. After step 3 the new service has replaced the baseline with its own WFP objects, and the old service deletes and re-registers the baseline at start. Full WFP cleanup (baseline replacement and uninstall) therefore searches every layer on the system for filters under SecureWall's provider key and deletes every sublayer that provider owns, whatever its key, so an older binary also removes layers and sublayers a newer version added. v0.5.0 is the oldest version a rollback can return to, so later versions may add layers and sublayers freely. A release may write only recovery journal records every upgradeable older version can read. VM case U14 checks the WFP side. The old version never reads a policy file the newer version wrote, because the snapshot is restored before the old service starts.

The upgrade never runs `/msi-cleanup` and never touches the persistent deny baseline, the Windows Firewall compatibility rules, the hosts file or the recovery journals. The baseline's provider names no service, so it stays in force while the service is stopped. From the old service's stop until the new service's first policy commit only the persistent and boot-time deny filters are active: external traffic is blocked in both directions, DNS and DHCP included, while loopback works. Open connections drop; the window is the service stop, the file swap and the new start, usually tens of seconds. Full-UI setup says so on its last page before Install. Pending prompts, prompt tokens and runtime-only grants are lost, as on any service restart; saved exceptions return with the new service. The audit-policy lease is released when the old service stops and taken again when the new one starts.

Starting either version mid-swap would lock files or run a half-installed version, so the automatic start paths check the marker. Controller repair and `/install` refuse to start the service. A controller that finds the marker shows "SecureWall is being upgraded" and exits, so it cannot hold `SecureWall.exe` open through file removal. All of this applies only while the marker exists and Windows Installer is running an installation (the `Global\_MSIExecute` mutex exists). A marker left behind by a power loss therefore never blocks SCM's boot start, `sc start SecureWall` or a later repair once no installation runs; SCM's own Automatic start does not read the marker at all. The start and restore steps accept only the marker of their own transaction. The controller's reconnect timer polls the service and never starts it, so it needs no check.

The MSI owns only the `InstallDir` and `Platform` values under `HKLM\SOFTWARE\SecureWall`, in its own registry view, and no longer deletes that key on removal, because the `FirewallRecovery` and `AuditRecovery` journals below it must survive the old version's removal during an upgrade. SecureWall's own subkeys and values (the journals and the marker) are always in the 64-bit view, whatever package installed it. Explicit removal deletes the rest of the key: `/msi-cleanup`, `/uninstall` and failed first-install rollback delete the journal subkeys (only when neither holds a restorable record) and the marker as their last step, and after an MSI removal commits, a commit-phase action deletes the key itself with `reg.exe` (64-bit view). A deferred delete would escape MSI rollback and lose `InstallDir` and `Platform` after a rolled-back uninstall; a committed removal implies both journals were restored and cleared. A journal kept because its restore failed keeps the key, minus the upgrade marker. `Platform` (`x64`, `arm64` or `x86`) names the installed package; an x86 package on 64-bit Windows keeps its values under `WOW6432Node`, where only another x86 package finds them, so cross-architecture upgrades are refused.

| Failure | Result |
|---|---|
| A check in step 1 fails (machine data, registration, service not running, a controller that cannot be closed) or the service does not stop in time | Upgrade aborts with no file changed. The restore step makes sure the old service runs and turns its restart actions back on. |
| MpsSvc or BFE is stopped before the upgrade | SecureWall's service depends on both, so it is already stopped. Step 1 refuses, the restore step cannot start the service while they are down (event 1001), and the baseline blocks external traffic. Start the Windows Defender Firewall and Base Filtering Engine services, then start SecureWall or reboot. |
| File copy, registry write or new-service start fails | Full rollback: old files, old policy snapshot, old shipped data, old service running with its restart actions. |
| The snapshot is missing or does not match its manifest at rollback | The old service is not started; the deny baseline keeps blocking; marker and snapshot stay for local-console recovery. |
| The restore step cannot start the old service | The service stays stopped and the baseline blocks external traffic. Its start type is still Automatic, so a reboot retries, and `sc start SecureWall` from an elevated prompt retries at once. The MSI error and Application event 1001 name the step. |
| Power loss or hard reset mid-swap | The boot-time and persistent baseline block external traffic at boot. The Automatic service starts whatever binary is present; if that fails, traffic stays blocked until local-console recovery. Windows Installer rolls back a suspended installation the next time an MSI runs, which runs the restore step with the kept snapshot. VM case U8 records the actual behavior at each stage. |
| The new service crashes after setup finished | Normal SCM restart actions; the baseline holds meanwhile. |

Nothing in the upgrade opens the network to recover connectivity: every failure ends in a running SecureWall or in the deny baseline. Because the old version stops itself, a defect in a released version's stop step cannot be fixed by a later package. Such a defect fails the upgrade closed (rollback, old version keeps running), and explicit uninstall followed by a fresh install stays the fallback.


### Emergency release when machine data is rejected

When `%ProgramData%\SecureWall` fails validation, the service exits at every start and `SecureWall.exe /uninstall` refuses to run, while the deny baseline keeps blocking external traffic across reboots. The supported way out is MSI removal at the local console: Settings > Apps > SecureWall > Uninstall, or `msiexec /x` with the installed product. Its deferred SYSTEM action (`/msi-cleanup`) detects the rejection before reading any machine data and runs the emergency release:

1. Require the LocalSystem token and a protected Program Files installation tree, then require the registered service to be this executable, running as LocalSystem in its own process.
2. Disable the service and its restart action, then stop it with the normal bounded graceful stop.
3. Skip hosts restoration. The original hosts backup exists only inside the rejected tree, so it cannot be trusted; the hosts file is left as it is.
4. Restore Windows Firewall compatibility rules and notification settings, and the audit policy, from their `HKLM\SOFTWARE\SecureWall` journals.
5. Delete only the filters, sublayers and provider under SecureWall's provider key, then the controller task and the service. The removal rules above apply: another provider's filter in a SecureWall-owned sublayer makes the release fail with the WFP state unchanged.

The release never reads file contents from the rejected tree and never repairs, moves or deletes it; the tree stays as evidence. The guard rejection itself is written to the Application event log (event 1000) before the release starts. Release warnings go to stderr and, while the service's event source exists, to the Application event log. Each release failure goes to stderr. The first failure of each step also writes one Application event 1001 under source `SecureWall` that names the mode, the failed step (for example Windows Firewall compatibility restore, audit policy restore or WFP object removal) and the exception; a later failure in the same step, such as the stop deadline after a failed stop request, writes no second event. A stop request that fails while the service stops anyway is not a failure and writes no event. A release that returns failure writes one more 1001 event with the exit code and the list of failed steps. These events use no machine-data path and do not point to `installer.log`. Each warning and failure also passes through the normal installer log, which validates the tree again first (reading directory entries, attributes and ACLs, not file contents) and appends to `logs\installer.log` only if the tree now validates, which happens only when the rejected object was removed or fixed during the run. If compatibility or audit restoration fails, the release stops before deleting WFP objects, returns failure, and the MSI rolls the removal back. The service stays Disabled and the baseline keeps blocking; fix the cause (for example start the Windows Defender Firewall service) and uninstall again. Review the hosts file by hand after a successful release.

The release is reachable from any LocalSystem process that runs the installed `SecureWall.exe /msi-cleanup` or `/msi-rollback-install`; normally that is the MSI's deferred actions, but an administrator can also reach it through any SYSTEM context, such as a SYSTEM scheduled task. The previous `/msi-cleanup` had the same reach and already removed the baseline without the application password, so the release adds no new authority. Non-SYSTEM callers are refused before any action. It reads no file contents from the rejected tree, which is the only reason the guard exists.

### Failed first-install rollback

If `/install` fails, the MSI rollback runs `/msi-rollback-install` before it deletes the payload. That rollback continues past hosts and audit restoration failures (their backups and journals are kept and the failures are logged), and, once the service has stopped and its registration validates, always removes the controller task and the service registration so a later fresh install is not refused. If the graceful stop, the termination of the validated service process or the registration check fails, the rollback returns failure before any cleanup and leaves the service and baseline in place. It deletes the deny baseline only after SecureWall's allow-all compatibility rules are confirmed gone. If they cannot be confirmed gone (for example, the Windows Defender Firewall service is stopped with a recorded rule set), the baseline stays and external traffic remains blocked. Start the Windows Defender Firewall service, install SecureWall from trusted media at the local console, and uninstall it to release the baseline. If the WFP removal itself fails, for example because another provider's filter sits in a SecureWall-owned sublayer, the rollback still removes the task and registration and the baseline stays; remove the software that owns the named filter and reboot first, because a new `/install` refuses the same state. The same emergency rules apply when the rollback finds machine data rejected.

SecureWall has no update feed and no update client. The TinyWall updater (descriptor check, installer download, and database and hosts downloads from `tinywall.pados.hu`) was removed from the source, so neither the service nor the controller contacts an update server. The application database and `hosts.bck` change only through the MSI's shipped-data refresh described above. A legacy `AutoUpdateCheck` value in settings or an imported `.tws` file is ignored. A core test fails if product sources regain the TinyWall feed host or an update download call.

Optional AI explanations require HTTPS, disallow redirects, and disclose the default payload: executable filename, unverified publisher, identity type, service name and package SID when present. Full executable paths are excluded; destination disclosure is opt-in. The user-selected provider receives that payload and bearer credential. Each field has C0/C1 control characters removed, is capped at 160 characters and is sent in double quotes that the system prompt marks as data. The controller reads at most 64 KiB of response body under one 30-second deadline and discards a larger body; the displayed explanation is capped at 4,000 characters, error text at 600, and the panel labels the output as AI-generated and not a SecureWall verdict.

The lookup runs in the controller, and `SecureWall.exe` is also the LocalSystem service image, so a path exception for it would give the service network access. The AI settings instead set the machine setting `AiAssistantEgress` through the authenticated pipe (`PUT_SETTINGS`, so the password lock applies). While it is on and the firewall is in Normal mode, full policy reloads add one permit at user-permit weight for the `SecureWall.exe` app ID, outbound TCP to remote port 443 only, with an `ALE_USER_ID` condition whose DACL denies SYSTEM, LOCAL SERVICE and NETWORK SERVICE before allowing INTERACTIVE (S-1-5-4) tokens. The service process never matches it. Explicit user blocks and blocklists still take precedence; BlockAll and active display-off blocking omit it; turning the assistant off clears the setting and the next reload removes the permit. The permit is not limited to the provider's host: any interactive-token process running the SecureWall image, including code injected into the controller, can reach any TCP 443 destination. Name resolution follows the existing DNS rules. Because the permit covers only remote port 443, the AI settings reject an endpoint URL on any other port, and a system HTTP proxy on another port is not supported (the request would be blocked). Turning the permit on or off first reads the current settings from the service and sends that fresh copy with the flag changed; if the read fails, nothing is sent. A settings change that toggles only this flag, in the same mode, keeps pending prompt tokens; every other policy change still revokes them. The exception editor and tray whitelisting by executable, process or window warn before saving a non-block exception for SecureWall's own image. Live behavior of the user condition is a VM check in `docs/HARDENING-VALIDATION.md`.

## Current assurance boundary

Pure-domain tests, native compilation, protocol serialization, and synthetic popup mode do not prove real WFP behavior. Production claims require the matrices in `docs/TESTING.md` and `docs/HARDENING-VALIDATION.md`, code signing, installer verification, and independent security review. PID/service attribution races, audit-lease recovery after crashes, VPN/WSL/IPv6 behavior, and packet-level startup/shutdown behavior remain explicit live-test boundaries.

## Legacy data and controller recovery

A clean TinyWall-only migration means uninstalling TinyWall and rebooting before installing SecureWall, with no preexisting SecureWall machine-data tree. SYSTEM setup can create a missing protected `%ProgramData%\SecureWall` directory. A prior SecureWall installation can leave a tree with inherited user-write permissions. Even a trusted owner cannot prove that its old policy or backups were never changed by an untrusted user. Rejection of that tree is required security behavior.

A generic MSI error, including error 1722, can mean that machine-data validation rejected the tree. The startup diagnostic names the protected directory and retains the underlying exception. Interactive controller startup can show that diagnostic; SYSTEM maintenance writes it to stderr and opens no dialog. Windows Installer does not capture stderr from EXE custom actions, and SCM discards it for the service, so a guard rejection also writes one Error line (event ID 1000) to the Windows Application log under source `SecureWall`. That line names the mode, the protected directory and the exception. A failed `/install`, `/uninstall`, `/msi-cleanup`, `/msi-rollback-install` or in-place upgrade step (`/msi-upgrade-stop`, `-restore`, `-start`, `-abort`, `-commit`) writes event ID 1001 with its exit code or exception and the path of `installer.log`. The emergency release after a guard rejection writes 1001 events that name each failed step and the final exit code instead of an `installer.log` path, as described under "Emergency release when machine data is rejected". The event write uses no machine-data path; the MSI registers the source, and an unregistered source still reaches the Application log without message text lookup. The deferred MSI action cannot show its own reason, so setup's failure page offers to open `installer.log` and the Windows Installer log (always written to `%TEMP%` through the `MsiLogging` property) in the default text viewer. A failed `/install` appends the service's SCM status, its exit codes and the `service.log` entries written during the attempt to `installer.log`. A guard rejection writes no `installer.log`; its reason is in event 1000. Capture the Application log, installer diagnostics and the directory, and preserve the VM snapshot before recovery.

Stop and use trusted manual recovery from a local console when validation fails. This build does not repair ACLs, import policy, or quarantine or delete rejected data. To remove SecureWall with a rejected tree, use MSI removal, which runs the emergency release described under operational safety; it bypasses the guard only to release SecureWall's own firewall state and never reads file contents from the tree. Do not blindly restore legacy writable configuration or backups into a new protected tree. Restoring policy into a new installation needs trusted installation media and independently verified policy; existing recovery records remain evidence. No live recovery actions were performed as part of this change.

Controller recovery starts only an existing service with the expected protected executable, LocalSystem account and dedicated-process registration. Missing registration requires MSI recovery; this MSI supports full removal followed by a fresh installation, not in-place repair. Pending deletion requires closing service-management handles or a reboot before retrying. Ordinary users authorize only a System32 `sc.exe start` request; the controller waits for SCM Running status. Administrator controllers also do not create services or reconfigure dependencies. Service creation remains a guarded SYSTEM installation operation.

Ordinary interactive controller logs use `%LocalAppData%\SecureWall\logs`. Elevated, SYSTEM, noninteractive, impersonating and service/installer logging paths use guarded machine storage and never fall back to user paths. Log destination providers are evaluated lazily, guard failures are swallowed without recursive logging. A text log that passes 512 KiB is renamed to `<name>.old.log`, replacing any older one, and a new file starts, so the first error of a restart loop survives one rotation. Service policy and recovery never consume user logs.

The review's proposed changes for findings 4 and 5 would release enforcement or cleanup protection after a required hosts operation failed. Those fail-open changes are rejected: retain failure and recovery evidence until restoration succeeds. Finding 6's proposed retention of prompt tokens across successful policy changes is also rejected. Revocation requires fresh evidence under the current policy generation; reduced popup churn does not justify stale authority. The one exception is a change that toggles only the AI assistant permit in the same mode (see the AI section above): it adds or removes only the permit for SecureWall's own image, so pending tokens for other subjects stay valid.
