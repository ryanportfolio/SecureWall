# SecureWall v0.5.0

Website: https://secwall.org/

This is an unsigned alpha prerelease for exploratory testing. Network Activity now names the process and services behind a blocked connection and the host name a program looked up, Ignore remembers the apps you dismiss, and from this version on a newer SecureWall installer can upgrade an installed one without uninstalling it first. It is not signed or end-to-end verified. The changes below were checked with unit tests, builds, installer validation and code review only; none of them has been tested on a live installation yet, and the in-place upgrade cases have not run on a test machine.

## Changes

### Network Activity shows more about each connection

- **Process and services for blocked rows.** Windows reports a firewall block without a process ID, so a blocked `svchost.exe` row showed no PID and an empty Services column. SecureWall now pairs each blocked row with the matching Windows Security log event (5157 for a blocked connection, 5159 for a blocked bind, which includes raw sockets) and shows its PID about six seconds after the block. For `svchost.exe` the Services column then lists the Windows services in that process. When more than one process could match, the PID stays empty instead of guessing. PIDs are worked out only while Network Activity is open, so a row from before you opened it can show no PID after a burst of later blocks.
- **Unblock and Close process on those rows.** Close process ends the matched process. Unblock on a matched `svchost.exe` row adds one rule per service listed in that row, where it used to offer a rule for all of `svchost.exe`. SecureWall keeps a PID only while a process with that path that started before the block still holds it.
- **Host names.** A remote address that a program on this PC looked up shows that name, for example `140.82.114.4 (github.com)`. The name comes from the Windows DNS cache, so nothing extra is sent on the network. On a shared hosting or CDN address the name can belong to a different site than the one this connection used. Addresses no program resolved through Windows DNS stay bare, and loopback, broadcast and multicast addresses get no name. Copy remote address and the web search use the address alone.
- **Always allow outcome.** When a new copy of an Always allow app (for example claude.exe after an update) is blocked once while SecureWall adds its rule, the row now reads "Blocked, then allowed by Always allow" instead of plain "Blocked".

### Ignored list

- **Ignore** in the blocked-connection popup now saves the app to a new **Ignored** tab in Manage, next to Always allow. Later default-deny blocks from that app stay blocked with no prompt, and Network Activity shows them as "Blocked (ignored)". The list never allows traffic. Remove an entry in Manage to be prompted for that app again.
- An entry matches the exact identity of the prompt: the exact file path for a program, the package for a Store app, and the service name and path for a service. A copy of the same program in another folder still prompts. Prompts for a shared Windows service host cannot be listed and keep the old five-minute cooldown.
- With a password set and SecureWall locked, Ignore asks for the password the way Allow does. Cancel, or a wrong password, keeps only the five-minute cooldown. Closing the popup with X also keeps only the cooldown.

### AI Assistant default

- The optional AI Assistant (the **?** on the popup) now defaults to OpenAI's `gpt-6.1-sol` with medium reasoning effort, replacing `gpt-4o-mini`. If you never changed the model, you are moved to the new default; a model you typed yourself is kept. Reasoning effort is sent only for `gpt-6.1-sol` on `api.openai.com`, so other models and OpenAI-compatible endpoints get the same request as before.
- A lookup no longer stops after 30 seconds, so a slow answer is not cut off. Closing the popup, or moving to the next prompt, still cancels it.
- No live request to OpenAI was made while testing this change.

### In-place upgrades start here

- v0.5.0 is the first version a newer SecureWall installer can upgrade in place. The upgrade stops the service, keeps a protected copy of your settings, rules and password, installs the new version and starts it again. If anything fails, setup rolls back to the previous version and its settings. If that version then cannot start, connections stay blocked until a restart or `sc start SecureWall` from an elevated prompt; [In-place upgrade](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/SECURITY.md#in-place-upgrade) has the recovery steps.
- While the service restarts, connections to other computers are blocked, usually for under a minute, and open connections drop.
- An installer for a different architecture (x64, ARM64 or x86) than the installed one is refused.
- The installer and its rollback have been checked by unit tests and Windows Installer validation only. The upgrade test cases in `docs/HARDENING-VALIDATION.md` (U1 to U16) have not run on a test machine yet, so the first real in-place upgrade (v0.5.0 to a later version) is untested.

## Downloads and installation

Use `SecureWall_x64.msi` on Intel/AMD 64-bit Windows, `SecureWall_arm64.msi` on Windows on ARM, or `SecureWall_x86.msi` on 32-bit Windows. Verify the download against `SHA256SUMS.txt`. All installers are unsigned. Keep local console access and recovery installers available offline. Service loss can leave external networking blocked, including DNS and DHCP.

**Upgrading.** v0.4.2 and older cannot be upgraded in place, so uninstall SecureWall in Settings > Apps once, then install v0.5.0. From v0.5.0 on, running a newer MSI for the same architecture upgrades in place, keeps rules, settings and the password, and blocks connections to other computers while the service restarts, usually for under a minute. Run setup at the computer's own keyboard and screen.

For this one-time uninstall from v0.4.2 or older:

- Download and verify the v0.5.0 installer first. Optionally export your settings (Manage, Maintenance tab, **Export Settings**; the export does not include the password) as a backup.
- Between removal and reinstall SecureWall does not filter anything; Windows Defender Firewall's own settings apply.
- The existing `%ProgramData%\SecureWall` folder, including your rules and password, is reused if it passes validation.
- When setup finishes, the tray app looks for applications it knows (such as Chrome, Edge, Firefox, Google Update, SmartScreen and Steam) and adds allow rules for any it finds. The rules for Chrome, Firefox, Steam and WinSCP also accept incoming connections on any port. Where you already have a rule for the same file, the two are combined, so a rule you limited to some ports or to outgoing traffic is widened. If the firewall has a password, it asks for it first; cancel to skip all of this. If you don't cancel, check those applications in Manage afterwards and edit their ports back; deleting a combined rule also deletes your original one. After that password prompt SecureWall stays unlocked until you lock it from the tray menu or after 10 minutes of inactivity. An in-place upgrade from v0.5.0 on does not run this step.
- If setup says SecureWall service deletion is pending, or that an existing SecureWall service must be removed, close Services and other service-management tools or restart Windows, then try again.
- If removal fails, stop. The earlier SecureWall stays installed, and external traffic may stay blocked. Keep `%ProgramData%\SecureWall` as it is and see [operational safety](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/SECURITY.md#operational-safety) and the [live testing guide](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/LIVE-TESTING.md#if-the-trial-breaks-networking).
- If v0.5.0 setup fails, use **Open SecureWall log** and **Open setup log** on the failure page and keep both logs. Also check the Windows Application event log for Errors from source `SecureWall`. Event ID 1000 means the data folder was rejected; do not change its permissions. Event ID 1001 means a setup step (such as installing or starting the service) failed; its message and the logs name the step. See [failed first-install rollback](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/SECURITY.md#failed-first-install-rollback) and [legacy data and controller recovery](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/SECURITY.md#legacy-data-and-controller-recovery).
- If v0.3.0 is installed, read the upgrade notes in [v0.4.0](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/releases/v0.4.0.md#downloads-and-installation) first.

**Switching from TinyWall.** Follow [before switching](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/LIVE-TESTING.md#before-switching) first. Uninstall TinyWall with its own uninstaller and reboot before installing SecureWall; setup refuses to run while TinyWall or its firewall provider is still registered. To go back to TinyWall later, uninstall SecureWall first and follow [rolling back to TinyWall](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/LIVE-TESTING.md#rolling-back-to-tinywall).

## Collect a diagnostic report

Read [the live testing guide](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/LIVE-TESTING.md) and [coverage map](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/docs/DIAGNOSTIC-COVERAGE.md). Download the source archive for this tag to obtain `tools/diagnostics`, or use a checkout of this tag. Run the collector with Windows PowerShell 5.1 as described in [its README](https://github.com/ryanportfolio/SecureWall/blob/v0.5.0/tools/diagnostics/README.md). It creates a local report and does not upload it.

Logs record software outcomes and observed filtering decisions. They do not prove packet delivery, absence of boot/crash leakage, installer rollback, hostile filesystem resistance or power-loss durability. The bundled blocklists do not automatically update. Review normal-use logs before drawing conclusions about live behavior.
